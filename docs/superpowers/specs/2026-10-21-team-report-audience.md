# 팀 업무보고 작성 기준

사용자가 이 세션에서 확정한 작성 기준.

- 독자는 다른 프로젝트 담당자와 H/W 담당자를 포함한 팀 전체.
- PIM·Wireless Lan·ETC 프로젝트를 중심으로 문제·조치·결과·적용 단계를 구체적으로 보존.
- 코드명·경로·커밋 ID·SHA·hash·srcversion 등 구현 식별자는 게시 본문에서 제외.
- 실제 릴리즈 버전과 측정·단축 시간(초·분), 용량·처리량·온도·전력 등 업무에 의미 있는 수치는 보존. 커밋·빌드 식별자 제외와 수치 삭제를 혼동하지 않음.
- 수치의 측정 대상·변경 전후·단위·조건·검증 범위와 완료·계획 상태를 원문대로 유지. 서로 다른 측정 구간을 합산하거나 단기 관찰을 장기 안정성 확인으로 확대하지 않음.
- 들여쓰기는 내용의 관계에 따라 사용. 상위 업무와 하위 조치·결과를 연결하고 단계 수를 일률적으로 맞추지 않음.
- 한 줄에 한 항목, 문장 종결은 작성·수정·확인 같은 명사형.
- ETC의 웹 GPT·MCP 터널링과 빌드 서버 운영은 서로 분리. 내용이 없는 분류는 생성하지 않음.
- 밑줄은 주요 성과, 제품 기능·신뢰성에 영향을 주는 문제, 협의·판단 사항을 대표하는 실제 항목에 표시.
- ETC도 같은 중요도 기준으로 판단. 같은 성과의 상·하위 줄 중복 강조 금지. 개수 권장 4~5, 상한 10.
- Redmine 게시·Slack 전송은 별도 승인 대상. 이번 실행은 로컬 생성·검증까지.

상세 원문과 수집 snapshot은 증거로 보존. 회의용 요약의 필수 분류만 프로젝트 루트로 조정하며 원래 상세 보고서는 기존 분류·검증 계약을 유지.

## 수치 근거 선택 계약

- 새 팀 요약 catalog에는 측정 대상·조건·변경 전후 값·단위·비교 관계를 소유하는 `M` 근거를 추가. AI는 해당 ID를 선택하고 결정적 확장이 고정 구절을 출력.
- 원문에서 닫힌 경계로 추출 가능한 읽기 쉬운 구절만 대상. 코드 경로와 구현 설명이 섞여 경계가 불명확하면 기존 scalar 검증을 유지.
- 측정 구절은 독립 불릿으로만 출력. 전체 밑줄은 허용하며 임의 접두·접미 재해석, 값·조건·단위·순서 변경, 중복 선택, 프로젝트 이동은 차단.
- 실제 릴리즈 버전은 suffix까지 하나의 근거로 보존하고 중립적인 버전 표기 불릿으로만 출력. 제작·설치·고객 전달 단계는 버전값에서 추론하지 않고 별도 원문 근거와 대조.
- 릴리즈 단계·상태는 버전이 포함된 같은 원문 절에서 명시적으로 닫힌 상태 표현으로만 취득하고 위치와 원문을 catalog에 결속. 다른 버전이나 예정·부정·취소·혼합 문맥의 근거로 완료 상태를 만들지 않음. 버전 불릿의 상위 단계 및 같은 부모의 바로 인접한 일대일 단계 설명도 검사. 인접 연결이 여러 가지이거나 근거가 불명확하면 중립적인 버전 표기만 허용.
- M이 원문 annotation을 소유하는 동안 자식 Q/V는 같은 span·프로젝트의 순서 있는 증거로 보존. raw와 표시 구절 및 무숫자 용어 사전을 catalog hash로 고정.
- 새 계약은 새 팀 요약 run에만 적용. 기존 scalar catalog·READY/게시 증거는 변경하지 않음. 유용한 수치 근거가 있는 프로젝트에서 이를 전부 생략한 출력은 차단.
